# Building-block refactor: functional and regression test plan

Status: planned tests, not execution evidence. All required cases below must be
mapped to actual test names before calling this refactor complete. Counts are
not the goal: cases can share fixture setup or parameterize the same assertion,
but cannot disappear behind a total suite count.

## Test strategy

Mock the Laya loader/predict boundary. Exercise actual JSON loaders, question
validation, rules, enrichment, preparation, reduction and flow code. Use real
TypeScript outline/extract operations in a small integration subset; ordinary
runtime tests need no Node process. No live model downloads or inference in CI.

Fakes assert exact submitted text/question names/types/criteria, model kwargs and
call count. They return raw predictions, never preinterpreted decisions. Keep raw
responses, expected enriched metrics and expected decisions separately to prevent
an expected value from being generated by the code being tested. Use a fixed small
choice distribution, noul values and score legend, including captured fixtures
already in tests/fixtures/laya where appropriate. Tests must not assume every real
model will answer the same way as those fixtures.

Three reusable helpers are enough: a temporary JSON catalog builder, a fake agent
recording calls, and small valid input/raw-response fixtures. Prefer existing test
helpers. Do not create a generic scenario runner or another configuration language.

## A. Preserve current behavior before changing callers

A01. Ticket triage original captured request: exact same two SDK question bodies,
    order of named definitions where meaningful, department answer and churn decision.
A02. Ticket second response: department below threshold and churn accepted; one
    rejection leaves the other decision intact.
A03. Method selection: readable method choices/signatures, sentinel, and separate
    multiple_relevant question exactly match current prepared payload.
A04. Method winner accepted plus multiple=no: same selected ID, label map, candidate
    map, decisions and null reason as current block.
A05. Parameterize method outcomes: rejected choice; none_or_unclear; rejected
    multiple; multiple=yes. Assert existing reason and selected_id=null for each.
A06. Empty candidates, exceeded candidate budget and duplicate signatures retain
    existing skip/no-selection behavior and make zero model calls.
A07. Duplicate names at distinct locations retain readable disambiguation; invalid
    duplicate IDs/labels and malformed candidates retain explicit validation failures.
A08. Both SDK payload and source mapping are independent copies; changes to one run
    do not mutate the supplied outline or the next run.
A09. Character budgets are measured using existing prompt-plus-compact-JSON formula,
    with exact boundary and one-character overflow. Source code is never silently truncated.
A10. Capture existing public return keys and signatures; legacy callers require no
    additional argument and receive no surprise BlockResult envelope.

## B. Catalog definitions and named defaults

B01. Load one shared rule for each of choice/noul/score and resolve by exact name.
B02. Load shared question and inline question; each produces the same valid SDK body.
B03. Block local question key differs from catalog name: response/rule binding uses
    local key; catalog identity never silently renames the returned answer.
B04. Missing file/name reports typed error with useful reference; no model load.
B05. Duplicate catalog names, local question names and duplicate JSON object keys
    fail instead of last-value-wins. Parameterize common accidental copy/paste cases.
B06. Malformed JSON, wrong top-level shape, missing required fields and unknown
    question_type fail with an actionable message.
B07. Exactly one of question_ref/definition: both and neither fail.
B08. Unknown rule reference fails before preparation or model loading; no default fallback.
B09. Catalog references cannot be absolute paths or ../ paths; names are identifiers.
B10. Loading from unrelated cwd resolves packaged defaults identically.
B11. Exact copies of four current policies preserve thresholds and condition order.
    Specifically assert multiple_methods_default has no distance condition.
B12. Intentional empty conditions accepts any validated answer; document it explicitly.
B13. Changing a loaded per-run rule/question cannot mutate cached catalog contents.
B14. Isolated wheel includes shared JSON, block.json, README and Python files; import
    and execute a mocked new block with cwd outside source checkout.

## C. Compatibility and override precedence

C01. Default call uses default rule and returns expected decision.
C02. Same fixed raw response with stricter named override becomes undecided; payload
    stays identical and exactly one prediction occurs per invocation.
C03. More permissive override accepts previously rejected valid answer. No alternate
    answer is invented by the rule.
C04. Partial override mapping changes only named question; others keep defaults.
C05. Empty override mapping equals no override.
C06. Unknown override question key and unknown rule name fail before model load.
C07. Parameterize all six wrong type pairings among choice/noul/score. ERROR records
    block/question/rule/expected/actual types; loader and predict both remain uncalled.
C08. Correct types for all three question kinds run successfully.
C09. Type-specific metric on wrong type (distance on choice, gap on noul) fails early.
C10. Invalid operator, nonnumeric threshold for numeric comparison and nonfinite
    threshold fail validation; no silent acceptance.
C11. Valid field absent from actual response yields existing undecided reason,
    not a crash or implicit zero. Cover missing action.act_probability.
C12. Whole-rule replacement: default gap requirement must not survive when override
    intentionally contains only answer_confidence.
C13. Call override then default again: second call uses untouched defaults.
C14. Per-call shared question reference override and inline body override both work.
C15. Unknown question override keys, missing criteria and changed question type fail.
C16. Override text/criteria are visible in actual model request; rule content, expected
    answers and internal candidate metadata are absent from that request.
C17. Compare default and override threshold boundary: equality passes gte, just below
    fails. Check two AND conditions with first-only pass, second-only pass and both pass.

## D. Inputs, preparation and block output contracts

D01. Ticket input {text:string} is accepted; missing text, nonstring text and nonobject
    input are rejected before preparation and model loading.
D02. Method input requires full outline shape used by existing code; malformed
    callable list, missing ID/name/signature and duplicate IDs fail clearly.
D03. Default preparation generates method choices using signatures and readable labels,
    retains sentinel and stores opaque IDs only in internal state.
D04. Injected preparation is called exactly once with validated input and copied
    effective question definitions; its changed text/criteria reach Laya.
D05. Injected preparation cannot bypass input validation.
D06. Prepared result wrong shape, missing/extra question, altered type, bad choice
    criteria or nonstring text is rejected before prediction.
D07. A preparer that calls outline utility produces a valid normal PreparedInput;
    runtime does not independently call outline again.
D08. Utility/preparation exception logs stage and preserves cause. No model call or retry.
D09. Explicit SkipBlock retains block-defined reason/state, empty decisions, skipped
    status and zero model calls. Unknown unexpected exceptions are not skipped results.
D10. Prepared state missing candidate map or invalid label mapping fails before
    reduction can return an incorrect method ID.
D11. Input and prepared payload remain unchanged after SDK fake deliberately mutates
    the copy it receives; next run has the correct default payload.
D12. Reducer output is validated: wrong selected ID or invalid output shape fails.
D13. Decision-rejected run has status completed, with undecided decision; distinguish
    from skipped and thrown errors in consumers.
D14. Blank text behavior matches documented generic/individual block contract; do
    not silently trim whitespace or invent defaults.
D15. Invalid max_candidates/max_input_chars values fail; exactly allowed/one beyond
    candidate limits and ordinary Unicode input use existing budget semantics.

## E. Prediction, enrichment and extraction

E01. Single-question block makes one SDK predict call and returns one decision.
E02. Two-question block makes one SDK predict call containing both questions and
    evaluates both independently.
E03. Validate raw response before enrichment; missing requested answer, wrong answer
    type and invalid probability values preserve explicit failures.
E04. Enrich once per requested question; spy on the real enrich function while
    asserting independently computed gap/entropy or distance. Do not enrich twice.
E05. Gap for 0.7/0.2/0.1 is 0.5; rule can use it without altering raw probabilities.
E06. Noul 0.8 has distance 0.3; a distance rule can reject/accept without flipping yes.
E07. Choice extraction uses validated SDK choice, preserving legacy behavior rather
    than substituting whichever choice a new implementation recomputes as largest.
E08. Noul values below 0.5, exactly 0.5 and above preserve existing no/yes boundary.
E09. Score extraction preserves legend, rounding and clamping on representative
    boundaries already supported by existing tests; no new interpretation scheme.
E10. Invalid raw JSON values, nonfinite numbers and response type mismatch do not
    reach successful reduction; existing ResponseError behavior remains intact.
E11. Raw input and question definitions remain unchanged after enrichment/rules.
E12. Extra unrequested response fields follow existing validated-response behavior;
    only requested questions create decisions. Do not expand output accidentally.
E13. SDK load failure and prediction failure preserve useful errors and do not retry.
E14. Logs contain prepared questions, raw response, enriched metrics, effective rule
    and final decision; no raw source in ERROR summary. Verify events against same run.

## F. Model configuration and reuse

F01. Config model identifier reaches loader unchanged.
F02. Explicit temperature reaches existing lang_temperatures load kwargs; None
    retains existing default behavior and omits optional override kwargs.
F03. Language handling matches existing RunConfig behavior; invalid config fails.
F04. Two runs with equal configs and shared registry load once, predict twice.
F05. Model A then model B load two distinct agents and dispatch to the correct one.
F06. Same model with different temperatures loads separately, as current registry does.
F07. A→B→A reuses A on third call without leaking B's config.
F08. New invocation registry loads anew; no hidden global cache introduced.
F09. Failed load is not cached; a later explicit call may load again. No automatic
    retry inside a single failed block call.
F10. Different rules/questions with unchanged config reuse the agent but submit
    their own current payloads. Rules never enter model load or predict arguments.

## G. Flow composition and migration

G01. Two independent fixture blocks called sequentially return separately named
    decisions; caller may choose either model/config and named rule override.
G02. First accepted answer causes second block call; opposite accepted answer skips it.
G03. Undecided first answer follows explicit fallback/stop branch; it is not treated
    as a negative answer by accident.
G04. Flow performs deterministic utility between blocks and passes its output into
    second input; ordering and call counts are exact.
G05. Method accepted AND multiple=no extracts exactly selected source. Multiple=yes
    or either undecided makes no extraction call.
G06. Actual TypeScript fixture with several methods: outline → V2 selection with mock
    Laya → extraction, asserting exact source and source identity.
G07. Existing optional fallback: same eligibility, bounded second call, same config
    selection, no retries after explicit negative or multi-method signal.
G08. Existing project-root resolution option, deadlines and dependency budgets pass
    through unchanged when migrating file_method_context consumers.
G09. Old and new block results match across A01–A10 fixtures; compare exact meaningful
    dictionaries, not just decided=true.
G10. Public compatibility imports and calls continue working after switching adapter;
    existing tests remain green without consumers adopting BlockResult.
G11. Flow catches configuration/input/SDK errors using its existing boundary; timeout
    remains distinguishable from ordinary model error. Verify preserved no-op reasons.
G12. No new block/flow automatically runs from hooks or on module import. Catalog
    import cannot instantiate agents.
G13. Offline experiment using current entry point still produces expected summary
    decision and useful error for invalid rule; do not redesign report format.
G14. Reverting caller switch restores old implementation while additive new modules
    remain importable. Prove with explicit old/new entry-point calls, not destructive git operations.

## H. Documentation and final acceptance

H01. A developer following README can add a minimal one-question block with shared
    default rule, invoke default and override, and interpret returned decision.
H02. A second example shows method input preparation and dynamic choices; clearly
    state utilities versus model operations and source input requirements.
H03. A wrong-type rule example documents logged ERROR and zero inference; examples
    use actual supported names/types and runnable Python imports.
H04. Packaging test executes the new interface from installed resources; no checkout
    or cwd dependence. Keep original isolated-wheel regression coverage.
H05. Complete relevant Python regression suite passes; final TypeScript suite passes
    or any pre-existing unrelated failures are explicitly identified and not hidden.
H06. Reviewer checks each case ID against test names, actual assertions and recorded
    execution. Report skipped/unimplemented cases explicitly, not as covered.

## Test bookkeeping template

For each implemented group add a short entry in the PR or checked-in verification
note: case IDs; test file/function names; command; result; date/commit; known skips.
One parameterized test may satisfy several cases only if assertions actually
exercise each one. Correct legacy tests are not forced to fail. New behavior must
have meaningful red evidence before its implementation where practical.

## Deliberately deferred beyond this demo

No parallel calls/thread safety, cross-process model sharing, hot reload during a
prediction, remote registries, multi-tenant catalogs, arbitrary user code sandbox,
fuzzing campaign, benchmark harness, large-scale filesystem adversarial cases or
runtime interface-generation system. Do not spend implementation phases building
these. Ordinary malformed JSON, missing names, wrong types, duplicate identifiers,
resource packaging and repeated-call isolation are required, not deferred.
